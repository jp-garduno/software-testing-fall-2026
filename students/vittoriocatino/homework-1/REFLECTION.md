# Reflection — Homework 1

This assignment made the relationship between small changes and a reliable history feel much more concrete. My main challenge was deciding what counted as one logical unit of work. At first, it was tempting to build the page and documentation together, then make a single large commit. Instead, I split the work into a structural branch, a styling branch, and a documentation branch. That choice made it easier to review each change, describe it clearly, and recover from a mistake without touching unrelated work. It also showed why a descriptive branch name is useful: before opening a file, I could understand the purpose of each branch.

The commands I found most useful were `git status`, `git switch -c`, `git add`, `git commit`, `git log --oneline`, and `git diff`. I used `git status` before every commit to verify the files being staged. `git diff` helped me confirm that formatting and content changes were intentional. The conventional commit prefix was another helpful habit because the history now communicates whether a change adds a feature, improves styling, or updates documentation. Creating three feature branches from `main` also reinforced that branches isolate work until it is ready to integrate.

For a team project, I will keep this workflow: start work in a focused branch, make small meaningful commits, test or review the change locally, and open a pull request with context for reviewers. I will use the PR description to explain both what changed and why it matters. I will also update my branch from the shared base before requesting review, so merge conflicts are discovered early. These practices should make collaboration safer, reviews faster, and project history easier for the whole team to understand.
