# Reflexión sobre el desarrollo con TDD

El efecto más claro de TDD en este sistema aparece en la separación de responsabilidades. Las primeras pruebas solamente necesitaban crear un libro y consultar sus existencias. Después surgieron las restricciones del socio y, finalmente, la coordinación de préstamos. Ese orden permitió mantener reglas locales en `Book` y `Member`, mientras `Library` administra operaciones que involucran varios objetos. El diseño creció a partir de ejemplos concretos, sin necesitar anticipar una base de datos, una interfaz gráfica o servicios externos.

Una decisión especialmente útil fue representar cada préstamo mediante un registro inmutable. Las pruebas del historial exigían conservar el evento de préstamo y agregar posteriormente su fecha de devolución. Si el sistema solamente hubiera guardado la lista actual de libros del socio, habría perdido información al devolverlos. La prueba hizo visible esa diferencia. Crear una nueva versión del registro al cerrar el préstamo también permitió conservar las instantáneas previamente consultadas, una propiedad comprobada de manera explícita.

El principal desafío del enfoque fue mantener pasos pequeños cuando una operación afectaba varios estados. Prestar un libro parece sencillo hasta considerar que el inventario puede disminuir antes de descubrir que el socio alcanzó su límite. Las pruebas de rechazo verificaron tanto la excepción como la conservación del inventario. Esto llevó a validar las restricciones antes de modificar objetos y, posteriormente, a compartir esa validación entre los puntos de entrada. La dificultad estuvo en elegir ejemplos que representaran consecuencias observables, sin acoplarse a los métodos auxiliares.

Las fechas presentaron otro reto. Consultar directamente el reloj del sistema habría producido pruebas dependientes del día de ejecución. La construcción de `Library` admite una función que proporciona la fecha. Así fue posible avanzar el calendario sin esperar ni simular servicios complejos. Los casos verifican el vencimiento exacto, el primer día de retraso, los cambios de mes y la devolución. Para las multas se utilizó `Decimal`, evitando introducir aproximaciones de punto flotante en cantidades monetarias.

Entre los beneficios observables están la retroalimentación rápida y la confianza para refactorizar. La suite completa permanece por debajo de dos segundos y permite revisar cambios frecuentemente. Extraer la búsqueda de participantes, centralizar las restricciones del socio y consultar una sola fecha por operación no requirió reescribir las expectativas. Los registros de las fases RED también muestran por qué una prueba era necesaria: primero faltaba una conducta y después la implementación satisfacía el ejemplo junto con los anteriores.

Frente a escribir pruebas al terminar, este proceso cambia las preguntas iniciales. En lugar de comprobar únicamente qué hace un método existente, obliga a decidir qué debe ocurrir en situaciones concretas. Aun así, una cobertura del cien por ciento no demuestra que todos los requisitos imaginables estén cubiertos. Por eso se añadieron pruebas de caracterización para contratos ya implementados, como aislar historiales y conservar inventario tras un rechazo. Esas verificaciones se distinguen de los ciclos RED para no confundir evidencia adicional con desarrollo de comportamiento nuevo.

TDD resulta apropiado para reglas de negocio deterministas, cálculos y operaciones con invariantes claras. En exploraciones visuales o prototipos descartables, exigir el mismo detalle desde el principio podría frenar el aprendizaje sobre el problema. La sorpresa más significativa fue que los errores aportaron más información de diseño que los ejemplos exitosos. En una siguiente iteración convendría definir antes los límites de la API pública y ampliar los ejemplos de invariantes. También sería necesario incorporar persistencia y concurrencia mediante pruebas de integración antes de considerar este modelo en memoria como un sistema listo para producción.
