# Personal Reflection: White Box Testing & Code Coverage

Completing Homework 5 has significantly elevated my perspective on software testing and quality assurance. Prior to this assignment, I often viewed testing primarily from a functional, black-box viewpoint—simply verifying whether an expected input produced an expected output. Delving into white-box testing, control flow analysis, and branch coverage shifted my mindset towards understanding how every internal path, conditional branch, and error handler behaves under pressure.

Building the TaskFlow system from the ground up reinforced how architectural decisions directly influence testability. Implementing clear interfaces for `TaskRepository` and `NotificationService` and injecting them into `TaskService` demonstrated the power of decoupling. It allowed me to write fast, fully isolated unit and integration tests that simulate edge cases—such as database write failures, duplicate title conflicts, and notification outages—without needing live infrastructure.

Achieving 100% statement and branch coverage was both challenging and rewarding. It required examining boundary conditions meticulously, such as title character constraints and complex state transitions. However, the most vital lesson I learned is that high code coverage is a means to an end, not the ultimate goal. A suite with 100% coverage is only as effective as the domain assertions it makes. Moving forward, I will continue applying these techniques to build resilient, maintainable software with meaningful test suites that provide genuine confidence in production releases.
