# Reflection: Coverage Challenge

Para este ejercicio escribí pruebas que recorren la validación de pedidos, los cálculos de envío, los descuentos, el total, el procesamiento y la estimación de entrega. En vez de perseguir líneas aisladas, agrupé las pruebas por comportamiento y utilicé casos parametrizados para las variaciones equivalentes, como los métodos de envío, los códigos de descuento y las fronteras de cantidad. Esto reduce repetición y deja claro qué regla de negocio cubre cada caso.

Los caminos más importantes fueron las validaciones tempranas. Un pedido puede fallar por artículos vacíos, campos incompletos, precios o cantidades inválidas, dirección incompleta y varios formatos de código postal. También cubrí los dos recargos de cantidad, el umbral de envío gratis, el cargo internacional y el tratamiento especial de `FREESHIP`. Para probar el límite defensivo de descuento configuré una tasa mayor al subtotal; aunque no forma parte de los códigos iniciales, confirma que el límite funciona si la configuración cambia.

Una cobertura alta no es sinónimo de pruebas buenas. Puede alcanzarse ejecutando una rama sin comprobar el resultado relevante, o creando pruebas demasiado acopladas a detalles internos. La cobertura es una señal útil para encontrar zonas olvidadas, pero no prueba que los requisitos sean correctos ni detecta escenarios que no se imaginaron. En producción buscaría una cobertura alta en lógica de negocio y errores críticos, pero priorizaría pruebas legibles, deterministas y centradas en riesgos. El porcentaje razonable depende del impacto: pagos, autenticación y validaciones requieren más evidencia que código de presentación sencillo. También combinaría estas pruebas unitarias con integración, revisión de requisitos y pruebas de extremo a extremo para ganar confianza real.
